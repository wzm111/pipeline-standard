# 阻塞时的专家短诊断

只在当前任务遇到明确阻塞时读取。复用现有主调度员与已配置的planner或scope_guardian，不新增常驻观察者，不按时间、阶段或每次失败自动召唤专家。模型按models.md解析并通过原生参数传入；请求不代表实际型号。

## 何时介入

- 同一检查失败，原开发已做一次定向修复，随后同根因复测仍失败；使用两份真实、顺序发生的失败证据。
- 开发与QA对根因或修复方向存在具体冲突，且已有两份可定位的当前任务审查记录。

第一次普通失败先由原开发定位。能按已有recipe纠正的控件状态、路径或样本问题先定向修正，不占用专家。无新证据、只是在等待进程/角色、准备摘要或重复询问进度时不触发。专家应在尚允许继续的第二次同根因失败后指导，避免把错误路径拖到第三轮；已到上限或进入人工等待时不得借专家恢复执行。

## 次数与上下文

每个未解决根因使用稳定case_id，最多一次指导尝试；只有明确的新根因才允许本任务第二次，总上限两次，跨专家角色合计，待接受、启动失败也占位。同根因不得换名再问，不能换task或run来规避同一交付的预算。跨真实新任务单独计算，不回填旧历史。

入口对同一命令/目录/用途/覆盖类别的检查采用保守归并：更换失败报告、输入或问题名不增加专家名额；它不能自动识别同一检查中的不同业务根因。明确不同检查或新的具体审查冲突才考虑剩余名额，仍受本任务两次上限约束。

先用`expert-prepare`核对证据与预算，未满足条件即继续原流程，不启动模型。brief只包含失败摘要、已尝试修复和必要代码片段，总长最多6000字符；完整日志、业务数据、凭据和整轮对话不得传入。准备入口只保存摘要hash/长度及技术引用，不保存正文。字符上限不是token上限；宿主未返回实际token时保持unknown。

首次创建使用最小上下文，Codex显式传`fork_turns=none`；不能把主会话整段历史fork进去。后续新根因只有在原专家仍适合且保留的上下文有限时才续用，并只发本次差量。不批量试多个型号，也不通过反复启动解决宿主容量问题。

专家仅做一次只读短诊断：给出根因判断与依据、最多三项修复建议、下一步最小验证；不自行修改业务代码、运行全量测试或再派角色。原开发执行建议，原QA验证。若高风险修复需要更强模型，按原授权分工由匹配 `high_risk_implementation` 路线的 developer 接手修复。方案和验证专家继续独立评审。指导后先实际执行和观察结果，禁止用原证据反复追问。遇到超时/失联按原宿主恢复规则保留现场，未确认停止不能当作已退出或再开一份。

## 调用边界

由调度员执行，用户不需要填写参数：

```sh
python3 -B <runner> expert-prepare --project <root> --receipt <receipt> \
  --json '{"case_id":"toggle-state","trigger":"repeated_failure","evidence":["<失败检查完整引用1>","<修复后复测失败完整引用2>"],"brief":"<失败摘要、修复尝试、必要片段>","local_fix_attempted":true}'
python3 -B <runner> expert-status --project <root> --run-id <run>
```

`trigger=review_conflict`使用两份当前qa/review引用；冲突含义由调度员负责，入口不声称能理解业务或根因。prepare不消费调用次数，也不创建角色；实际派发在`role_dispatch.begin(..., advice_case="toggle-state", ...)`中重新核对并占位，随后仍须真实调用宿主、accepted和complete。预算拒绝发生在宿主调用之前。普通必要审查不变，不得用普通审查名称重复同一专家诊断。

首次可见进度说明“为何现在介入、已尝试什么、剩余次数”；返回后只报告可执行结论和验证结果，不逐条转发推理或长报告。记录只能证明已接入边界的声明与请求，不能拦截未接入调用或证明宿主实际prompt/token受限。

专家指导不修改QA三轮上限、不清除FAIL/CONCERNS、不补授权或自动通过验收；范围扩大、登录/解锁、发布与豁免仍走原人工闸口。是否有效看介入后的问题解决和返工记录，不预先承诺节省token或固定提速比例。
