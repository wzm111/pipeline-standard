# 高风险双专家评审

复用 scope_guardian 和 tester，分别由不同执行者担任方案与验证专家，两者均独立于本任务的开发。仅在共享逻辑影响多个入口、支付/权限/数据完整性、跨系统交付、同类漏检反复发生，或用户/契约明确要求双专家时启用。普通任务沿用现有流程。阻塞短诊断仍走 expert-advice.md 的独立预算。

1. **开发前审方案。** scope_guardian 根据任务目标、改动边界和调用方检查计划。只列适用项，包括共享入口、正常与失败路径、跨系统版本依赖、发布顺序及关键线上回读。每条明确可观察的预期、验证方式和应完成阶段。把必验项落入现有计划与 check-plan 的 required coverage，保留方案结论和未覆盖范围。方案未通过时按原范围评审轮次修订。
2. **候选冻结后验结果。** tester 使用同一清单及当前任务的候选、QA 与检查引用。逐项区分通过、失败、缺证据、按既定阶段待验证，并报告负责范围与是否阻断。已有有效证据直接复用，只补必要覆盖。高风险派发前解析 tester 的 high_risk_verification 路线，传入 risk=high 及已知复杂度，按宿主原生反馈记录实际模型。无法取得独立验证结论时保留待验。
3. **打回与交付。** 每个确认的阻断缺陷留下可复现检查或可执行验收步骤。由原验证专家仅复核修复项和受影响范围，必要终验与 QA 上限沿用原规则。只有方案关键假设或边界变更才召回方案专家。调度员用现有 QA/acceptance 门禁核对已登记的必验项。分别报告本地验证、线上版本与实际业务验收。已约定上线后观察的事项保留待验条件及后续动作。

工具校验已登记的证据及覆盖，影响面和业务清单的完整性由方案与验证专家判断。

使用 managed CLI 时，在派发方案专家前用现有 `report --kind dual_review` 登记本任务要求，JSON 可用 `{}`。先建立可供评审的 check-plan，调整必验清单时使用新计划引用。方案专家返回且实际停止后写 `solution_review`，包含 `gate`、`dispatch_id`、`requirement_ref`、`plan_ref` 和简短评审结论。验证专家核对当前证据、返回并实际停止后写 `verification_review`，包含 `gate`、`dispatch_id`、`solution_ref`、按 QA 返回顺序列出的完整 `checks` 引用和逐项结论。两个报告的 gate 只有明确通过才填 PASS。缺证据时可用同一计划的 QA 返回定位缺项，补齐后新建报告复核。计划改变、检查引用更新或最新评审失败后，旧通过结论不能继续放行。

续跑先说明上一轮阻塞是否解除及依据。启动前核对 run 归属和两位专家的模型能力，未确认的项目记录为待核实。只读复查可以单独反馈。用 progress.md 的加粗标识明确当前动作、最近结果、阻塞和下一步。

该门禁适用于显式登记的 managed 当前任务，在 QA、完成及当前任务的发布收口校验登记证据。角色记录来自调用者观察到的宿主反馈，工具无法独立读取宿主或识别未声明的高风险任务。
