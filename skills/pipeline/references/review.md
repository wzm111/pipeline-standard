# 高风险双专家评审

复用 scope_guardian 和 tester，分别由不同执行者担任方案与验证专家，两者均独立于本任务的开发。仅在共享逻辑影响多个入口、支付/权限/数据完整性、跨系统交付、同类漏检反复发生，或用户/契约明确要求双专家时启用。普通任务沿用现有流程。阻塞短诊断仍走 expert-advice.md 的独立预算。

1. **开发前审方案。** scope_guardian 根据任务目标、改动边界和调用方检查计划。只列适用项，包括共享入口、正常与失败路径、跨系统版本依赖、发布顺序及关键线上回读。每条明确实际入口、可观察的预期、已有检查或待补验证及应完成阶段。优先沿用用户或调用方实际使用的接口。把必验项落入现有计划与 check-plan 的 required coverage，保留方案结论和未覆盖范围。方案未通过时按原范围评审轮次修订。
2. **候选冻结后验结果。** tester 使用同一清单及当前任务的候选、QA 与检查引用。逐项区分通过、失败、缺证据、按既定阶段待验证，并报告负责范围与是否阻断。已有有效证据直接复用，只补必要覆盖。高风险派发前解析 tester 的 high_risk_verification 路线，传入 risk=high 及已知复杂度，按宿主原生反馈记录实际模型。无法取得独立验证结论时保留待验。
3. **打回与交付。** 每个确认的阻断缺陷留下可复现检查或可执行验收步骤。由原验证专家仅复核修复项和受影响范围，必要终验与 QA 上限沿用原规则。只有方案关键假设或边界变更才召回方案专家。调度员用现有 QA/acceptance 门禁核对已登记的必验项。分别报告本地验证、线上版本与实际业务验收。已约定上线后观察的事项保留待验条件及后续动作。

工具校验已登记的证据及覆盖，影响面和业务清单的完整性由方案与验证专家判断。

## 核对需求与实现

评审开始时固定需求来源、比较基线和当前候选。分支或 PR 用实际合入目标的共同祖先作为比较起点。本地候选包含未提交改动时，核对纳入交付的暂存、未暂存和新文件，并排除无关改动。基线不明或差异为空时先核对范围。缺少可信需求来源时，把需求符合性记为待核实。

现有评审角色分别给出两类结论。按改动风险取必要深度，低风险任务可在同一次复查中核对两类，高风险任务沿用现有双专家分工。

- **需求符合性**：从原始需求逐项追到真实调用入口、可观察结果和验收证据，找出遗漏、部分实现和超出授权的行为。方案专家先标出影响面，验证专家独立核对候选，检查共用逻辑的其他受影响入口和原有行为。计划漏列的关键项补进现有检查计划。
- **工程质量**：从候选差异追到受影响的调用方，按项目契约与已有设计检查回归。按改动类型核对异常、重试、并发或旧数据兼容。改动涉及共享规则时，沿受影响的入口核对是否各自实现了默认值、校验或异常处理。发现重复或分歧时列出具体调用方、触发条件及遗漏会造成的行为差异。关键用例从公开入口核对状态变化或输出，期望值来自需求、已有契约或独立样本，避免用实现自身算出预期。

发现按「需求或规则来源、文件与行号、触发条件、实际与预期、证据或待补验证」记录。将确认的问题、缺失证据和可选改进分别写明，并沿用当前 QA 判级。未核验的必验项继续待验。复测复用仍有效的证据，仅重核修复和受影响范围。

参考 [Matt Pocock 的 code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md) 与 [tdd](https://github.com/mattpocock/skills/blob/main/skills/engineering/tdd/SKILL.md)。

## 把重复漏审补进检查

同类问题反复漏审或单次遗漏后果明显时，在现有短复盘记录遗漏的入口或条件、原检查为何未覆盖，以及下次要补的断言或可执行验收步骤。把本任务仍需验证的项纳入现有检查计划。跨任务的改进写明适用条件和检查落点。已有项目回归用例或验收清单可承载时，在授权范围内补入，超出当前范围的改进记入待办。未执行的检查保留待验。

## 记录与门禁

使用 managed CLI 时，在派发方案专家前用现有 `report --kind dual_review` 登记本任务要求，JSON 可用 `{}`。先建立可供评审的 check-plan，调整必验清单时使用新计划引用。方案专家返回且实际停止后写 `solution_review`，包含 `gate`、`dispatch_id`、`requirement_ref`、`plan_ref` 和简短评审结论。验证专家核对当前证据、返回并实际停止后写 `verification_review`，包含 `gate`、`dispatch_id`、`solution_ref`、按 QA 返回顺序列出的完整 `checks` 引用和逐项结论。两个报告的 gate 只有明确通过才填 PASS。缺证据时可用同一计划的 QA 返回定位缺项，补齐后新建报告复核。计划改变、检查引用更新或最新评审失败后，旧通过结论不能继续放行。

续跑先说明上一轮阻塞是否解除及依据。启动前核对 run 归属和两位专家的模型能力，未确认的项目记录为待核实。只读复查可以单独反馈。用 progress.md 的加粗标识明确当前动作、最近结果、阻塞和下一步。

该门禁适用于显式登记的 managed 当前任务，在 QA、完成及当前任务的发布收口校验登记证据。角色记录来自调用者观察到的宿主反馈，工具无法独立读取宿主或识别未声明的高风险任务。

新 CLI start 和 task-start 必须提供 --review-risk low|medium|high|unknown 和 --review-reason。high/unknown 自动保留双专家义务，即使漏写 dual_review 也不能验收通过。旧 Python 调用保持兼容，已有义务在未作新范围决策时继续继承。明确同交付承接使用 --continuation-of <同 run 已结束任务>；旧任务的要求继续生效。真正无关的新目标用 --independent-goal 及独立风险决策和理由建立新任务；省略该标志会继续保留原义务。delivery_from 承接也保留双专家义务；可复用原检查，当前阶段仍需独立专家核对。

开发派发或显式进入 implementation 前必须已有本任务方案 PASS。收口复查方案早于首次开发记录；对已实现成果的补充审查，task-start 显式加 --retrospective，不能将其宣传为开发前评审，该模式仅供只读复核。

activate 前检查发布前必验类别及独立验证结论，并在登记 attempt 的锁内再次核对。发布后 smoke 仍留到上线后验证。缺少独立结论时不能启动激活命令，smoke 和恢复诊断仍可用于补充证据。

主调度员取宿主实际可见进度消息，用 report --kind progress_feedback --name <本轮名> --json '{"messages":[{"text":"<实际已发送文本>","sent_at":"<可选真实时区时间>"}]}' 登记。入口立即执行格式检查，仅保存技术检查结论，正文不落盘。双专家 QA 缺少合格反馈记录时保留 CONCERNS；补正后的下一条真实反馈另建记录，旧问题保留在历史中。该检查只证明调用者提交的消息格式，发送真实性和语义完整性仍需对照宿主，不能拦截未接入的聊天发送。

登记新计划时查看 `plan` 返回的 `review_delta`。方案引用变化时，按新增、移除、命令或输入变化、执行顺序变化和必验类别变化核对差量。只有排序调整也需确认新引用，原有效检查可继续复用。该提示只比较已登记的方案，最终验收仍核对当前独立评审证据。
