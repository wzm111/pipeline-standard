# 用户可见的执行进度

用于执行中的主动反馈及回答“现在干什么、是否还在跑、到哪一步”。用户不必打开内部报告。主会话汇总必要角色的实际反馈，不转发原始日志、凭据或业务明细；不为进度创建角色、启动测试或另一条流水线。

## 标识与内容

用固定标识符和加粗文字，颜色仅作辅助；不依赖聊天客户端支持自定义HTML颜色或终端ANSI转义。纯文本仍保留方括号标签，日志中不混入颜色控制字符。

| 标识 | 使用条件 |
| --- | --- |
| 🔵 **[进行中｜开发/测试/构建/审查]** | 正在执行一个具体动作，有本会话动作或新宿主/进程反馈依据 |
| ✅ **[已完成｜具体步骤]** | 该步骤有实际成功结果，说明覆盖范围；单项通过不代表全部交付完成 |
| 🟠 **[修复中]** | 已有依据的缺陷正在修正，说明问题、影响面和随后要补的检查 |
| ⏳ **[等待中]** | 正在等已知命令、角色或外部结果，说明等什么和最近有效反馈 |
| 🔴 **[需你处理]** | 必须由用户操作，给出具体动作及恢复后的验证标准，沿用原人工等待规则 |
| 🔎 **[待核实]** | 缺宿主反馈、状态冲突或非零结果尚未分类，先核对已有进程/日志/角色，不直接说正常或卡死 |

每次通常一至两行：**当前动作；最近有效结果；阻塞/等待（有则写）；下一步**。第一次说明本需求范围和当前阶段，后续只发变化，不复述整份计划。

首次分工及范围实质变化时，主调度员说明谁做哪个模块、共享文件归谁、依赖项为何排队；直做/串行也给具体原因。分工尚未调用宿主时写“计划”，begin后写“已请求”，原生工具接受后才写“已启动/续用”，实际返回后再写“已返回”。累计子智能体图标、记录中的working或requested_model都不能单独证明真实并行或实际型号；用对应原生开始/续用及结果核对。`progress`中的调度摘要只投影已登记边界，不是宿主探针。

格式示例，尖括号必须换成真实记录，拿不到就省略或写未知：

> 🔵 **[进行中｜构建]** 正在构建前端，已运行〈本步骤实际时长〉；最近完成：〈检查及结果〉。下一步：核验构建产物。
>
> ⏳ **[等待中｜独立审查]** 等待测试角色的身份隔离结论；最近有效反馈在〈实际时间〉，目前没有新结果。下一步：根据结论补缺口或收口。

## 核查实际反馈

主调度员在阶段切换、角色返回、关键检查结果和人工等待时使用已有 `progress --format text` 的首行标识。需要自行组织正文时，用下方命令生成消息，直接将返回行作为聊天反馈。正文写实际动作、最近结果、阻塞与下一步，按当前事实选择状态。观察与发送仍由主调度员完成。

```sh
python3 <skill>/scripts/progress_feedback.py --draft <<'JSON'
{"status":"等待中","step":"独立验收","body":"本地检查已通过，正在等待 tester 返回。收到反馈后会核对同一候选。"}
JSON
```

工具不可用时手工沿用本页格式。用 `--stdin` 核查宿主实际可见消息，区分已生成草稿与已发送反馈。

需要核查已输出消息时，将宿主实际返回的可见进度文本作为JSON数组经stdin传入`python3 <skill>/scripts/progress_feedback.py --stdin`，每项仅含`text`和可选的可靠`sent_at`（含时区）；不扫描业务日志、不保存或回显正文。工具检查六种固定标识、加粗标签和非空正文，并只报告已有时间戳的间隔候选；没有时间不估算，超过90秒的间隔不能单独证明违规（可能处于未返回宿主调用）。`format_valid`只表示格式，动作/结果/阻塞/下一步的具体性及真实性仍需复核，policy-ack也不能代替。该入口不拦截每次发送、不自动发消息或纠正另一聊天；有权限的执行者在下一条反馈修正即可，不重启任务或重跑检查。

## 何时反馈

- 开始、阶段切换、重要检查开始/结束、发现阻塞或修复完成时及时反馈。不要直到最终答复才汇总，也不要只说“继续处理中”“正在验证”。
- 长操作超过约60秒仍未结束时，在下一次工具返回或可安全读取原会话输出时给一条具体状态；继续等待则通常每60至90秒简报。用有界yield/poll读取原命令会话或已有角色反馈，不缩短业务检查超时，不另起进程重跑，不密集轮询或给每条快照写进度。
- 无新结果也如实说“仍在等待，上次有效反馈是…”，明确接下来核对什么；不能为刷新进度伪造工作、重复同值更新state或声称即将完成。宿主长调用尚未返回时不能承诺实时推送能力。
- 原聊天的执行进度与旁观自动监听分开：执行者负责上述反馈；监听默认只报有意义变化，只有用户明确要求周期状态才调整提醒，不能靠每次心跳刷屏代替真实执行信息。

## 依据与边界

进度同时区分`task_execution`（执行段起止）、`delivery`（run登记完成或外部待办）和`host_feedback`（显式宿主反馈）。task-end只表示执行段结束，不能显示成验收完成；结束段之后的新检查不混入该段进度。人工等待只提示原操作，不把run/active标记当执行者仍在工作。即使run登记completed，进度仍不重验QA，也不证明线上或平台收件已通过。

已取得原生宿主反馈时，可用progress的`--host-status running|idle`及idle时的`--host-ended-at <真实停止时间>`，只读注明依据；没有反馈保持unknown，不为此启动探活。过早的idle反馈标stale；idle与仍登记的角色/检查冲突时标待核实，不能自动取消、重启或清锁。查询不发送聊天消息，执行者仍须在实际里程碑和长操作返回时按本页反馈。

一次`progress`同时返回当前task的检查、待返回宿主观察、未结束操作与最近QA登记结论，不读日志正文；QA字段只代表已登记，不重新验收。连续查询可传`--after-milestone <上次milestone_id>`，无变化仅返回紧凑delta，调用方继续保持安静，不再逐条tail旧日志。脚本不创建轮询或自动发送消息。

执行者可在阶段或重要结果变化后调用 `pipeline_cli.py progress --project <项目> --run-id <当前run> --format text`，直接取得固定标识及当前任务、登记成功步骤、当前检查/角色、剩余项和阻塞；默认JSON还返回`milestone_id`供按实质内容去重。主会话结合实际宿主反馈转成简短中文步骤，不能仅粘贴内部ID代替说明。该查询只读当前任务的有界元数据，不读日志/凭据、不重新哈希源码、不启动检查或定时器。`recorded_success`只表示记录时成功，当前有效性仍由原QA核验；`last_result_at`只来自实际检查结束时间，和`state_updated_at`分开。无计划、未采集或截断项保持未知。脚本不会自行发送聊天消息，长工具调用未返回时仍受宿主反馈能力限制。

复用当前上下文、现有state/当前task、running_checks、operation_spans和角色最近反馈。必要时只读`pipeline_cli.py status --project <项目> --run-id <已知ID> --recovery`取紧凑指针，再只看当前步骤需要的记录；它不是进程探活或验收证明。进度查询不启动run、不清锁，也不因查看而修改updated_at。

`running`、`.active`或登记为working都不能单独证明正常运行。区分“登记执行中”“宿主仍活跃”“进程有新输出”和“检查已通过”；无可靠宿主信息时标待核实。状态时间戳只表示状态写入，不能冒充最后实质结果时间。仅因耗时长不能认定停滞、取消执行者或重复启动。

没有检查计划的直做任务也展示当前任务边界内已登记检查的最新结果，无需为了看进度新建计划或拆 task。只列 test/check 结果，同身份后续失败覆盖旧成功；这仍是登记摘要，不重新验收证据，无计划时剩余步骤继续标未知。

时长取当前task或本步骤真实起点，不从多日旧run创建时间倒推；旧阶段/纯排队未知则保持未知。并行时段不相加，测试数量不当耗时，不编造完成百分比、ETA或token。阶段和activity实际改变时仍走原update/观察接口；本页不放宽QA、复用、发布或人工闸口，也不要求正在运行的旧上下文中断重做。
