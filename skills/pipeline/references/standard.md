# standard 流程

下文 state.md 是旧格式名称；使用 run_state.py 时统一写对应 runs/<run_id>.json，不维护双份状态。结束步骤必须先确认执行者停止和本run归属，再调用finish；不能为满足“清理”而删除未知活动锁。

## 默认直接执行（优先于下方委派流程）

1. 当前 agent 读取 developer 规则，初始化最小 state.md，在会话内列简短计划与验收项并直接实现。无需 planner/dev/qa 子 agent、context、plan 或 retro 文件；角色文件的交接路径要求只在委派时适用。
2. 无实质歧义且在用户授权内时发简报后继续。契约明确要求每次人工确认时遵守；新增依赖、禁区、公开接口/数据、权限/支付/安全、范围不确定时保留闸口 1。已批准的相同范围不重复确认。
3. 默认一个交付批次，不按文件数、任务数或预计时长机械拆批。实际运行核心验收与契约要求的终验命令；UI 行为需运行态验证。相同代码、配置、依赖、环境下的成功检查只跑一次，记录命令、范围、时间、退出码和输出位置。无法确认结果有效性时重跑；失败后只复测失败项与影响面，最多 3 轮。
4. 收口写 qa/final.md（摘要、验收证据、未验证项、人工待办），不把未执行检查标通过。人工模式直接给提交建议；自动提交创建 releaser 并复核契约 ④ 节。state 置 done，追加 metrics，清理 .active。
5. 只有用户/契约要求独立检查或实际风险需要时创建 reviewer，按 guardian/tester 规则检查差量、复用有效证据并补测缺口；文件数不是独立评审触发器。需要复杂规划或独立批次并行时才进入下方委派流程；跨系统/高风险升级 thorough。
6. 每次增加角色、拆批、重跑检查前明确具体收益，无收益就省略。区分实现/验证耗时与交接/报告/等待开销；不承诺固定加速倍数。用户预算到达 80%、CONCERNS 或异常时读取 operations.md，报告完成项、剩余检查和可交付范围。

## 按需委派：计划与闸口

1. 初始化 state.md(status/stage/batches/pending/next)，创建 planner，传 `context/base.md` 与 `context/planner.md`。
2. planner 发现实质歧义时只返回带建议答案的问题；无歧义时写 `plan.md`。任务 >4、预计开发 >40 分钟或天然分层时按依赖/文件归属拆为 2–4 批，通常每批 2–5 个任务；没有并行或提前 QA 收益时保持单批。
3. plan 只记录任务、验收、涉及文件、来源定位、快速/终验测试层和基于 metrics 的 ETA，不复制基线正文。
4. 用户给 `--auto` 或契约允许低风险自动进入时，发送计划简报后继续；新增依赖、禁区、公开接口/数据、权限/支付/安全、范围不确定时必须等待闸口 1。
5. 上述风险信号或用户/契约要求独立评审时创建 guardian 评审 plan，最多 2 轮；保留同一 guardian 供终验复用。仅文件数量增加不触发。

## 开发、QA 与收口

1. 创建一个持久 developer；首批可测产物冻结后读 `qa-loop.md`并创建持久qa。仅确有独立、可完成的验收准备工作时提前创建；后续批次只用 follow-up 发送 context 差量。并行前核对生成目录及其他共享资源，冲突则顺序执行或显式隔离。
2. qa 完成所有批次后只读 `qa/index.md`，运行终验层一次并写 `qa/final.md`。若已有 guardian，唤醒它只读 plan、qa/index.md、qa/final.md 做最终范围检查；否则调度员据这三份精简 artifact 收口。
3. 人工上线模式由调度员直接输出变更摘要、提交建议和人工待办，不创建 releaser/release-notes。自动提交模式才创建 releaser，并严格按 PIPELINE.md ④ 节执行。
4. 把既有数据写入简短 retro，state 置 done，追加 metrics.tsv，展示 qa/final.md 中的人工确认项并清理 `.active`。
5. 终验失败、预算预警、CONCERNS 或异常时读 `operations.md`；正常 PASS 不加载。
