# 便携版流水线(单 Agent 降级模式)

> pipeline-standard 的便携形态,给没有 subagent / hook 机制的 agentic 编码工具用
> (Codex CLI、Gemini CLI、Cursor 等)。一个 agent 依次扮演全部 5 个角色,串行执行。
> 方法论、闸口、批次、打回上限与 Claude Code 版完全一致;执行保障的降级项见文末。
>
> 本文件是 `agents/*.md` 的蒸馏版,只保留核心纪律;完整角色定义见同仓库 `agents/` 目录。

## 用法

把本文件接入所用工具的自定义命令机制,触发时附带任务描述:

- Codex CLI:拷到 `~/.codex/prompts/pipeline.md`,以自定义命令触发
- Gemini CLI:包一层自定义 command 引用本文件
- Cursor / 其他:直接把全文 + 任务描述粘进对话

(各工具的命令机制以其官方文档为准。)

以下「你」指执行任务的 agent 本体。

## 前置

1. 读项目根的 `PIPELINE.md`。不存在 → 停止,告诉用户「本项目还未接入流水线」,契约模板见 `templates/PIPELINE.md`,等其补齐后再来。
2. 规模分流(拿不准就问用户):
   - **小任务**(预计改动 ≤2 个文件、无新依赖):跳过第 2 步自我评审,其余不变。
   - **标准任务**:走全流程。
3. 工具自检(可选):契约 ③ 声明的外部 CLI 逐个 `command -v` 探测,缺失告知用户;能装则装,装不上跳过对应项并在测试报告注明,**不阻断**。
4. 断点、裁决一致性与通知(可选):
   - 断点:`tmp/pipeline/state.md` 存在且 status 非 done → 上次 run 未完成,向用户确认续跑还是新开;运行中在阶段切换/等待用户/异常停止时更新它(status / stage / batches / pending / next 五要素),提前停止置 aborted。
   - 裁决一致性:`tmp/pipeline/rulings.md` 存在 → 读入已有裁决;续跑时遇到相同问题直接按文件结论执行。CONCERNS 裁决后必须追加写入 rulings.md,避免多会话结论冲突。
   - 通知:契约声明了 webhook 时从环境变量读 URL,闸口等待/待裁决/完成三时机各发一条纯文本;未设置静默跳过。

## 流程

### 第 1 步:澄清 + 拆解(角色 B)

- 先查实质性歧义(多种合理解法 / 缺验收口径 / 范围边界不清)→ 有则不写计划,直接给用户「待澄清问题清单」,每条附建议答案。
- 无歧义 → 拆解,计划写到 `tmp/pipeline/plan.md`:
  - 任务 >8 个分批(每批 ≤10):`plan.md` 只写头部 + 批次索引,明细写 `plan-<批次>.md`;≤8 个单文件全量。
  - 每任务一行 `- [ ] T编号:内容`,下方附验收标准(可执行/可测试)、涉及文件、来源条目编号。
  - 头部注明任务总数、批次数、预估时长量级;里程碑级(>10 任务或 >半日)末尾附「拆分建议」供人工定夺。
- 契约引用的大文档(PRD/Roadmap)用搜索定位章节再读,不全文通读。
- 若 `tmp/pipeline/retro.md` 存在(上次 run 的复盘),用其实测数据校准本次预估;给出两类口径供闸口 1 决策:
  - **墙钟时间**:单 agent 串行执行,约为"任务数 × 5–8 分钟"量级;
  - **人力时间**:同一上下文无并行,与墙钟时间接近,用于评估 token/人工投入,不作为排期口径。
- 标注"预估为量级参考,实际受打回轮次、API 配额、需求歧义影响"。

### 闸口 1:计划确认(人工)

向用户展示计划摘要 + 任务数/批次数/预估时长(里程碑级附拆分建议);可附一句让用户设本 run 上限(时长或批次数),设了则在进度快照对照、≈80% 预警。**等用户明确确认后才继续**。

### 第 2 步:范围自我评审(角色 A,≤2 轮;小任务跳过)

切换到评审视角,对照契约 ① 需求基线与 ② 规范逐条核 plan:有没有漏需求条目、超范围、违反禁区与架构约束。
**注意「换装」**:重新打开基线文档对照,不凭刚写完计划的记忆自评。
发现问题 → 修订计划再审;2 轮仍不过 → 停下向用户汇报分歧点,人工裁决。

### 第 3 步:开发 → 测试 批次循环(角色 C/D,打回 ≤3 轮/批)

无批次的计划视为单批。每一批次:

1. **角色 C 开发**:checkbox 逐个勾选;批内任务完成后按契约 ③ 测试命令自测全绿 → 向用户一行简报「批次 X 交付」。
2. **角色 D 测试**(换装:把刚写的代码当别人写的):
   - 测试范围 = 该批任务 + 验收标准;结论只能来自**实际运行的命令输出**,不凭印象。
   - 对抗式找茬:边界值、异常路径、契约声明的专项扫描都跑到。
   - 复测收敛:被打回后的复测只覆盖打回项复现 + 修复影响面 + 快速命令层;首轮已过且修复未触及的重命令不重复跑,报告注明收敛范围。
   - 报告写 `tmp/pipeline/qa-report.md`,头部四行:`gate: PASS | CONCERNS | FAIL` / `round: 第 N 轮` / `batch: 批次名(无批次写 ALL)` / `summary: 一句话结论`。
   - `FAIL` → 切回角色 C 修复,修完 D 复测;单批 ≤3 轮,到顶停下汇报,不酌情放行。
   - `CONCERNS` → 把非阻断问题列给用户裁决:豁免 → 该批封版;不豁免 → 回 C 修。**无论结果如何,把裁决追加写入 `tmp/pipeline/rulings.md`**(问题/建议/实际裁决/理由/关联文件),供后续会话作为事实源。
3. 进度简报:每批 gate 出结果后给用户一行(批次名、总进度 N/M、gate 结论、下一步)。

### 第 4 步:验收(角色 A)

对照 plan(及批次详情文件)验收标准 + qa-report.md 做最终验收,关键验收点亲自打开代码 / 跑命令抽查。
不过 → 向用户汇报,人工决定回第 3 步还是调整计划。

### 第 5 步:上线建议(角色 E)

产出 `tmp/pipeline/release-notes.md`(变更摘要 + Conventional Commits 提交建议 + 人工待办)。**必须包含「人工执行命令」区块**:把建议的 `git add`/`git commit`/`git push` 命令逐行列出,并注明"本命令须由人类在闸口 2 执行"。**不做任何 git 写操作与部署**。

### 闸口 2:提交与上线(人工)

先把本次 run 的既有信息落 `tmp/pipeline/retro.md`。固定头部(供 planner 下次校准用):

```markdown
# Retro

- run_id: 可空
- 任务总数: N
- 批次数: M
- 计划 ETA: X 人日 / Y 小时
- 实际时长: Z 小时(墙钟)
- 平均每任务墙钟: Z/N 分钟
- 主要偏差原因: 简述
```

正文再写:每批打回轮次、CONCERNS 次数与裁决结果、自检缺装项、一行经验。再展示 release-notes.md 摘要。**你不执行任何 git 写操作与部署**;git 提交、追踪矩阵打勾、部署由用户手工执行——流水线到此结束。

## 与 Claude Code 版的差异(降级项)

| 能力 | Claude Code 版 | 便携版 |
| ---- | -------------- | ------ |
| 角色上下文 | 每角色独立 subagent 冷启动,tester 看不到 dev 的实现思路 | 同一上下文,对抗性靠「换装」纪律模拟 |
| 批次节奏 | qa 测上一批与 dev 开下一批并行重叠 | 串行(开发完整批才测) |
| 禁区 ⑤ | PreToolUse hook 机器硬拦截越界写 | prompt 自觉,无硬拦截 |
| 打回循环 | dev⇄qa teammate 直聊,不占调度员上下文 | 单上下文内切换,无此需求 |
| 闸口 / 批次 / 打回上限 / 契约 | — | **完全一致** |

## 纪律

- 打回轮次上限是硬约束,到顶必须停下来汇报,不许「酌情放行」。
- 一个项目同一时刻只跑一条流水线:`tmp/pipeline/` 下的 artifact 是单例,并行触发会互相覆盖。
- **严禁执行 git 写操作**:commit/push/add/tag/reset/merge/deploy 一律由人类在闸口 2 执行;你只把建议命令写进 release-notes.md。
- mock/dev-only 守卫只能限定在明确 mock 路由;基础设施端点(sitemap/robots/health/manifest/openapi/_nuxt/PWA sw)必须显式豁免,不得被 mock 断言误杀。
- 任何阶段出错/超时,向用户报告当前阶段与已有产物,不要静默重试超过 1 次。
