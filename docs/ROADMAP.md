# pipeline-standard 分期建设路线图

更新日期：2026-10-26  
当前基线：v3.8.0（已发布）  
文档状态：开发规划；下列任务默认未完成，不代表功能已实现或已通过验收。

## 1. 产品目标与边界

让个人开发者和小团队通过自然语言完成项目接入、需求开发、验证和恢复，同时能够分别配置 Claude Code 与 Codex 的角色模型。

核心价值按优先级排列：

1. 普通需求的交付时间接近直接使用编码智能体，不再因为固定流程放大为 4–6 倍。
2. 必要验收真实执行，能区分已验证、未验证、受阻和失败。
3. 用户不需要编辑配置文件、记参数或理解 agent 编排。
4. 两端共享项目约束，各自适配模型、权限与工具能力，差异明确可见。
5. 有可复现的案例和度量，证明提效，而不是用角色数量证明成熟度。

当前定位是可试用的研发流程工具。行业竞争力是待验证目标，不能把发布版本、配置解析测试或文档规则视为生产成熟度证明。

近期不建设：独立 IDE、通用工作流平台、模型交易/代理服务、自动购买模型权限、无授权跨提供商调用、复杂配置 UI。暂不自动选择“最便宜/最强”模型，也不承诺无条件完成时间或 token 降幅。

相关实现：`skills/pipeline/`、`agents/`、`hooks/`、`tests/`、`init-project.sh`。本表按本次规划时的版本记录，后续每期验收更新，不倒推旧版本已经具备新能力。

## 3. 全流程交互标准

### 默认体验

- 用户说“帮我实现搜索”，自动识别项目与验收方式，必要时接入并继续原需求。
- 用户说“配置模型”，优先展示当前环境已确认可用的选择；无法读取名单时给“继承当前模型”的可靠选项。
- 用户说“架构改成……”，只改对应运行时和角色，不重新配置所有项目。
- 用户说“继续”，恢复现场；说“进度”，只读汇报；说“停止”，终止本 run 执行者并保存现场。
- 收口回答做了什么、验证了什么、还缺什么。报告路径是补充，不是让用户自行查找答案。

### 询问规则

可从项目和已确认偏好推断的信息不问；每轮通常只问一个影响结果的问题。没有关键歧义时零配置开工。需要用户选择时提供少量可执行选项，不展示长 JSON 或要求填写目录、模型 ID、flags。

设置与执行分离：“保存了模型偏好”不能说成“正在使用该模型”；设置不触发研发 run、不清除活动锁、不启动整条角色链。已有有效授权不重复询问，风险变更和外部发布仍遵守实际权限。

版本号是候选发布标识，不是预先保证的交付日期；每期验收后才能发布。阶段可以拆补丁，版本以实际兼容性决定。

| 第二期：模型配置可靠闭环 | v3.9.0 | 选择、保存、解析、应用、验证、回退 | 第一期能力口径 | P0 |

## 5. 第一期：基线与诚实反馈

目标：先把“支持什么、没验证什么、为什么慢”说清，防止错误配置和未经证实的提速宣传。

任务：

- [ ] P1-01：README 的模型入口以“配置模型，由智能体展示可用选项”为主，具体型号标成非通用示例。
- [ ] P1-02：明确四类状态：可用、不可用、无法验证、当前宿主不支持；账号权限和工具支持分别记录。
- [ ] P1-03：统一无模型/无权限/无独立选模能力时的短对话，提供继承当前模型、重选、暂不设置等适用操作。
- [ ] P1-04：定义度量数据格式和计时边界，保留原 metrics.tsv 兼容，不把缺失值记成 0。
- [ ] P1-05：选取第一批 6 个代表性需求，冻结初始代码、验收清单和运行配置，建立直接开发与 skill 开发基线。
- [ ] P1-06：记录当前主会话直通、独立角色启动、实际模型可见性差异，形成首轮兼容记录。

交付物：更新的入口文案、能力/失败状态规范、基准需求清单、首轮原始记录与分析。建议后续落在 `docs/benchmarks/`，没有数据时不创建空的“成功报告”。

验收：没有权限的模型不能报告为可用；不能读取名单时不伪造名单；已确认可用才推荐具体选项；首轮 6 个需求均有两种方式的结果或明确阻塞记录。可用性名单只是预检证据，不等于启动成功。

不包含：大规模重构、自动换供应商、未经测量的固定节省百分比。

## 6. 第二期：角色模型配置可靠闭环

目标：从提示词约定提升为有明确输入、状态、错误处理和验证证据的配置过程。

任务：

- [ ] P2-01：建立最小运行时适配层，分离能力发现、配置解析、启动参数转换和启动结果记录；不把账号能力硬编码在通用层。
- [ ] P2-02：完善安全保存：局部更新、原子替换或等价保护、写前检查、写后回读；保留另一运行时、无关角色和未知扩展字段。
- [ ] P2-03：覆盖项目/个人/本次优先级、恢复继承、删除项目覆盖、仅变更 effort、切换模型清除不兼容 effort。
- [ ] P2-04：Codex 实际启动验证：正确传入 model/effort、满足宿主 fork 限制、传最小任务上下文；检查自定义 agent 设置覆盖请求参数的情况。
- [ ] P2-05：Claude 实际启动验证：工具覆盖优先、必要时生成专用角色文件、不改共享安装源；覆盖加载刷新、继承固定 frontmatter 与角色文件命名冲突。
- [ ] P2-06：对不可用模型仅按用户已授权策略回退；无授权先给短选择，不不断重试型号，不产生隐藏 API 支出。
- [ ] P2-07：记录请求值、传参、运行时实际反馈和回退原因；不返回实际模型时标 unknown。
- [ ] P2-08：仅偏好设置不额外启动 agent；用户明确要求本次使用指定开发模型时，只委派必要角色。

必须验证的异常：型号不存在、权限拒绝、effort 不支持、名单不可读、网络失败、限流、配置损坏、未知版本、写入失败、活动 run、角色文件已存在、模型可见但子 agent 不可用。

交付物：最小适配实现、配置行为测试、两端真实启动报告、失败/回退测试记录、使用说明。

验收：全部配置行为测试通过；两端至少各完成一次继承和一次显式模型选择的真实调用；不支持的宿主明确标受限。实际模型不可观测时不能计入“已证实切换成功”样本。成功/失败路径均无跨端覆盖、静默换模或权限扩张。

不包含：让 skill 安装云端模型、购买权限或替用户更改全局默认模型。

## 7. 第三期：交付效率实测优化

目标：证明流程带来可接受的开销和质量收益，定位耗时而不是盲目减少检查。

### 实验设计

比较三组：A 为同一宿主直接执行，B 为 skill 默认直通，C 为 skill 按需多角色。A/B 固定模型与 effort；C 若使用不同模型，作为独立实验报告，不能把模型差异当作流程优化收益。

样本逐步扩充至至少 12 个：小修复、普通功能、跨模块功能各至少 4 个。选取 UI、接口、状态逻辑、测试修复等任务；高风险任务单独记录，不要求强行使用同一种低成本模式。

每个实验使用相同的初始代码、依赖、需求与验收清单，隔离工作区，保留用户改动。执行顺序交错，记录冷/热缓存与网络等待，避免前一轮的解法和产物污染后一轮。第一期允许每组单次探索；进入发布判断前，每个样本 A/B 至少各重复两次，报告波动。

### 度量口径

| 指标 | 定义 |
| --- | --- |
| 总墙钟时间 | 接受任务到完成验收/明确停止，包含人工等待 |
| 执行墙钟时间 | 总墙钟减人工等待，仍包含工具/网络等待 |
| 开销比 | 同任务 B 的执行墙钟 / A 的执行墙钟；先按任务求比，再看分布 |
| 流程耗时 | 交接、重复阅读、状态/报告维护；需有事件证据，无法归因则标未知 |
| token | 实际可观测的输入、输出、缓存与子 agent 用量分别记录；不可见留空 |
| 验收质量 | 预先冻结的核心验收通过率、遗留缺陷、返工次数 |
| 人工干预 | 用户被要求做决定/手改配置/手动恢复的次数和原因 |
| 资源消耗 | agent 数、工具调用、重复检查次数；并行耗时不简单相加当墙钟 |

### 优化任务

- [ ] P3-01：增加必要阶段事件记录，建立关键路径；日志本身不应变成大量新工具调用。
- [ ] P3-02：统计不必要的规划、交接、重读、报告和等待，按贡献排序修复。
- [ ] P3-03：验证单批直接收口、按需角色的实际行为，防止规则互相矛盾又退回固定链路。
- [ ] P3-04：建立测试证据失效条件，涵盖代码、配置、依赖、环境与外部服务变化；缺少可信指纹就重跑必需检查。
- [ ] P3-05：测量批次并行的真实收益，禁止共享工作树测试被并发写入污染。
- [ ] P3-06：输出优化前后同任务结果和失败案例，报告样本数、中位数、P80、波动与数据缺口。

候选验收目标（规划目标，不是当前承诺）：普通低/中风险任务 B/A 中位数 ≤1.3、P80 ≤1.5；可观测总 token 比中位数 ≤1.3；核心验收全部通过，不能用删测试、少做需求换时间。样本量不足或 token 覆盖不足时该指标为“未证实”。高风险任务按缺陷发现和返工减少另行评价。

门槛需在实验前冻结；基线显示不可行时记录原因并重新评审，不在看到结果后偷偷移动门槛。未达标优先修复，必要时缩小默认编排范围，不能宣称已经解决 4–6 倍耗时。

## 8. 第四期：完整对话操作与恢复

目标：用户能从“首次接入”一直走到“验收完成”，无需理解内部文件和状态机。

- [ ] P4-01：自动识别新/旧项目、单仓/多包项目；项目根不明确时只询问根目录选择。
- [ ] P4-02：基于真实脚本生成测试层与目录边界；没有测试设施时明确缺口，不写假命令。
- [ ] P4-03：已有契约精确补全，绝不覆盖禁区、用户确认策略或其他 hook；验证 init-project 对已有 matcher 的合并行为。
- [ ] P4-04：引入可辨认的 run_id、锁归属与生命周期，区分活动任务、过期锁、正常暂停和崩溃。
- [ ] P4-05：验证“查看进度”无写入，“继续”不从头重跑，“停止”先停止执行者，“新开”不覆盖未归档现场。
- [ ] P4-06：统一预算预警、CONCERNS 与失败提示：给完成项、剩余项、建议动作，用户一句话即可回应。
- [ ] P4-07：配置操作不被研发状态误拦，也不能通过删除锁绕过保护；缺权限时展示具体受限动作。

验收场景至少包括：空白项目、已有完整契约、占位符模板、多包仓库、无测试项目、配置损坏、正常继续、崩溃后恢复、另一执行者仍在运行。

验收：低风险明确需求无需用户手填文件；零关键歧义场景不额外询问；没有因恢复丢失用户代码、覆盖规则或双 run 并发。业务必要澄清与权限提示单独统计，不以减少提问为由隐瞒风险。

## 9. 第五期：双端兼容和稳定发布

- [ ] P5-01：建立按宿主版本记录的能力矩阵：选模、effort、agent、续跑消息、hook、实际模型可见性。
- [ ] P5-02：扩展自动测试：安装、初始化幂等、配置优先级/保存、语法、引用路径、坏状态恢复和防护边界。
- [ ] P5-03：分别测试 Claude hook 与 Codex 流程校验，保留其保障差异；任何缺失 hook 不得报告已开启硬拦截。
- [ ] P5-04：覆盖 v3.8.0 到新版本的读取/升级路径，不主动重写旧项目；未知配置版本保留原文并解释。
- [ ] P5-05：形成版本发布清单：证据、已知限制、兼容范围、中文说明、精确 tag/commit、回退步骤。
- [ ] P5-06：自动化只跑本地/隔离测试；需要账号、真实模型或产生费用的测试单独标记，不能作为普通安装的隐藏动作。

验收：自动回归通过；两端目标版本各有真实会话验收记录；旧配置无丢失；回退保留用户数据；不能支持的宿主明确列为受限，而非“通用兼容”。

## 10. 第六期：真实项目试点与对外推广

- [ ] P6-01：在至少 3 个经授权项目中试点，覆盖至少两类技术栈，累计至少 20 个需求；不得自动读取或修改未授权项目。
- [ ] P6-02：收集耗时、验收、人工干预和配置失败，优先解决重复出现的问题。
- [ ] P6-03：整理可公开的匿名案例；不发布私有代码、凭据、客户数据或未获授权的执行日志。
- [ ] P6-04：提供三条主要使用路径：直接开发、设置模型、恢复任务；高级配置放次要文档。
- [ ] P6-05：明确适用与不适用场景，发布可复现实验步骤及已知失败情况。
- [ ] P6-06：根据证据评审 v4.0.0 是否成立；未达标准继续小版本迭代，不因计划版本号强行发布。

验收：试点数据完整可追溯，第三期性能门槛有足够样本支撑；无未处理的数据丢失、静默换模、越权写入问题；新用户能不手改配置完成一个代表性需求。对外提效数字必须附模型、环境、样本与测量方法。

## 12. 每期执行和更新约定
